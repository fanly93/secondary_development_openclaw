# OpenClaw 系统架构说明

## 1. 文档目的与阅读范围

本文从**顶层架构**描述 OpenClaw 的整体设计思路与模块划分：数据与控制流如何在「客户端 → 网关 → 渠道与自动回复 → Agent 运行时 → 扩展能力」之间贯通。

**范围约定**：

- 仅依据仓库**根目录及 `src/` 一级子目录**等顶层结构归纳功能模块，并标注**代码出处（仓库根相对路径）**。
- **不展开**到具体函数、类或文件级实现细节。
- 与下列四份二开分析文档形成互补：`phase1_client_communication.md`、`phase2_gateway_client_integration_spec.md`、`phase3_channel_io_interface_spec.md`、`phase4_agent_runtime_architecture_spec.md`。

---

## 2. 整体设计思路

### 2.1 一句话概括

OpenClaw 是一个**以 Gateway 为统一控制面与协议中枢**、以 **Agent 嵌入式运行时为推理与工具执行核心**、以 **Channel 插件与自动回复管线为消息出入口**、以 **插件体系为横向扩展面**的多渠道 AI 网关系统。

### 2.2 分层心智模型

| 层次               | 职责（概念）                                                                           | 与四份 Phase 文档的对应关系              |
| ------------------ | -------------------------------------------------------------------------------------- | ---------------------------------------- |
| **客户端层**       | CLI、Web 控制面、原生 App（operator/node）通过统一协议连接 Gateway                     | Phase1                                   |
| **接入与网关层**   | WebSocket 主协议、HTTP 兼容面、Hooks、插件 HTTP 路由；鉴权、配对、方法路由、会话与事件 | Phase2                                   |
| **消息与渠道层**   | 入站上下文标准化、出站载荷与适配器；与各聊天/通讯面对接                                | Phase3                                   |
| **Agent 与编排层** | 命令入口、模型与目录、工具/技能/MCP、会话与记忆、Compaction 等运行时策略               | Phase4                                   |
| **扩展与运维层**   | 插件发现与注册、密钥与配置、定时与唤醒、任务账本、Doctor/迁移等                        | Phase2～4 中分散提及，本文在顶层统一标出 |

### 2.3 核心设计原则（架构视角）

1. **协议统一**：控制面交互优先走 Gateway WebSocket 文本帧（req / res / event），避免各端自定义分叉协议（Phase1、Phase2）。
2. **边界清晰**：渠道差异收敛到统一 I/O 契约（`MsgContext`、出站适配器等），再进入同一套 Agent 调度链路（Phase3）。
3. **运行时可扩展**：Channel、Provider、工具、HTTP 路由、服务等通过插件注册进入同一运行时，而非在核心中硬编码枚举一切扩展（Phase2、Phase4 与 `plugins/`、`plugin-sdk/`）。
4. **安全与信任分层**：连接侧（配对、device token、scope）、执行侧（沙箱、审批、策略）与配置侧（密钥解析）分工，而非单点「全部信任客户端」（Phase2、Phase4）。

## 3. 仓库顶层结构总览

以下为**仓库根目录**主要文件夹及其在整体架构中的角色（**出处**：各路径均为仓库根相对路径）。

| 顶层路径                                       | 架构角色                                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| `src/`                                         | **核心后端与 CLI**：Gateway、Agent、自动回复、渠道核心、插件加载、配置、任务、定时等 |
| `extensions/`                                  | **捆绑/工作区插件树**：渠道扩展、模型 Provider 扩展等（与核心通过插件契约衔接）      |
| `apps/`                                        | **原生客户端**：Android、iOS、macOS 及共享 Kit（与 Gateway 的通信实现落在此树）      |
| `ui/`                                          | **Web 控制面（Control UI）**：浏览器侧 Gateway 客户端与界面资源                      |
| `packages/`                                    | **独立子包**：与主仓协同的 SDK/契约包等（如 memory-host、插件包约定等）              |
| `docs/`                                        | **产品与技术文档**（对外行为与协议的权威说明之一）                                   |
| `skills/`                                      | **技能样例与模板**（与 Agent 侧 skills 机制配合，非运行时唯一来源）                  |
| `scripts/`                                     | **构建、发布、检测、辅助脚本**                                                       |
| `test/`、`test-fixtures/`                      | **自动化测试与夹具**                                                                 |
| `qa/`                                          | **QA 场景与自动化相关资产**                                                          |
| `assets/`、`vendor/`、`dist/`、`dist-runtime/` | **静态资源、可选厂商依赖、构建产物**（运行时以发布/构建配置为准）                    |
| `Secondary-development-requirements-sorting/`  | **二次开发需求与架构梳理文档**（含 Phase1～4 与本说明）                              |

**入口与产物（根目录文件，概念性标注）**：

- `openclaw.mjs`、`package.json`：CLI/包入口与导出（含 `openclaw/plugin-sdk` 等对外子路径）。
- `pnpm-workspace.yaml`：monorepo 工作区边界（核心、`extensions`、`ui`、`apps` 等协同方式）。

## 4. 核心后端：`src/` 一级目录功能地图

以下按**架构职能**归纳 `src/` 下**一级子目录**（仅列与整体架构强相关的目录；个别测试或单文件入口不逐一枚举）。

### 4.1 Gateway 与控制面

| 模块路径                | 顶层功能                                                                                                                            |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `src/gateway/`          | **Gateway 实现**：WebSocket 服务、HTTP 服务编排、RPC 方法分发、会话/聊天/节点相关服务端能力、OpenAI 兼容 HTTP 适配等（Phase2 主体） |
| `src/gateway/protocol/` | **Gateway 协议定义**：帧结构、方法/事件与校验模式（与 `docs/gateway/protocol.md` 等文档对应）                                       |

### 4.2 Agent 运行时与模型侧

| 模块路径              | 顶层功能                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| `src/agents/`         | **Agent 命令与嵌入式运行**：模型解析与回退、工具集、技能、MCP 物化、会话写锁与 attempt 管线等（Phase4 主体） |
| `src/context-engine/` | **可插拔上下文引擎**：与默认/扩展上下文策略相关的注册与实现边界（Phase4）                                    |

### 4.3 消息入口、自动回复与「渠道核心」

| 模块路径                                  | 顶层功能                                                                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `src/auto-reply/`                         | **入站派发与回复管线**：统一 `dispatchInboundContext`、`dispatchInboundMessage`、回复调度与配置驱动回复等（Phase3 与 Agent 的接合面） |
| `src/channels/`                           | **核心渠道实现与插件类型**：内置渠道逻辑、Channel 插件契约在核心侧的实现（Phase3；扩展插件在 `extensions/`）                          |
| `src/infra/outbound/`（归入 infra，见下） | **统一出站投递**：与 `ChannelOutboundAdapter` 协同的总线（Phase3）                                                                    |

### 4.4 插件平台与对外 SDK

| 模块路径          | 顶层功能                                                                 |
| ----------------- | ------------------------------------------------------------------------ |
| `src/plugins/`    | **插件加载、注册表、清单、CLI/HTTP/服务注册**：运行时扩展的枢纽          |
| `src/plugin-sdk/` | **对外插件 SDK**：扩展作者允许依赖的稳定 API 面（与 `extensions/` 配合） |

### 4.5 配置、密钥、路由与配对

| 模块路径       | 顶层功能                                                                              |
| -------------- | ------------------------------------------------------------------------------------- |
| `src/config/`  | **配置模型、持久化、会话元数据存储与 transcript 路径等**（跨 Gateway / Agent / 渠道） |
| `src/secrets/` | **SecretRef 与解析管线**：运行时将配置中的秘密引用落地（与 Gateway/CLI 协同）         |
| `src/routing/` | **会话键、Agent 路由与相关约定**（与 Phase3/4 中的 SessionKey、路由一致）             |
| `src/pairing/` | **渠道配对消息与配对存储等**：与「谁能发消息给 Agent」相关                            |

### 4.6 定时、任务、唤醒与系统事件

| 模块路径     | 顶层功能                                                                                |
| ------------ | --------------------------------------------------------------------------------------- |
| `src/cron/`  | **定时任务服务**：计划、执行、与 Gateway 方法及运行时的衔接                             |
| `src/tasks/` | **任务账本与 TaskFlow**：长异步、子 Agent、后台执行的可观测与状态（与 Phase4 编排相关） |
| `src/infra/` | **横切基础设施**：心跳唤醒、审批投递、配对文件、执行策略辅助等（多模块复用）            |

### 4.7 ACP（独立控制面协议路径）

| 模块路径   | 顶层功能                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------- |
| `src/acp/` | **ACP 控制面与会话管理**：与嵌入式 Pi 路径并列的另一条执行内核相关实现（Phase4 所述「双路径」之一） |

### 4.8 CLI、命令与终端体验

| 模块路径        | 顶层功能                                                         |
| --------------- | ---------------------------------------------------------------- |
| `src/cli/`      | **CLI 框架、Gateway RPC 客户端、进度与交互**（Phase1 中 CLI 侧） |
| `src/commands/` | **各子命令实现**（agent、doctor、status 等对用户可见入口）       |
| `src/tui/`      | **终端 UI**：偏交互式会话与控制                                  |
| `src/terminal/` | **表格、调色板等终端输出组件**                                   |

### 4.9 媒体、语音与工具周边能力

| 模块路径                                                                                                            | 顶层功能                                               |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `src/media/`、`src/media-understanding/`、`src/image-generation/`、`src/music-generation/`、`src/media-generation/` | **媒体流水线与生成类能力**（多由工具或 Provider 触发） |
| `src/tts/`、`src/realtime-transcription/`、`src/realtime-voice/`                                                    | **语音合成与实时语音相关**                             |
| `src/mcp/`                                                                                                          | **MCP 相关核心桥接**（与 Agent 侧 MCP 配置/传输配合）  |

### 4.10 Hooks、安全与其它横切

| 模块路径                                  | 顶层功能                                                             |
| ----------------------------------------- | -------------------------------------------------------------------- |
| `src/hooks/`                              | **内部 Hooks 装载与触发**：自动化与外部事件接入（Phase2 Hooks 概念） |
| `src/security/`                           | **安全审计与策略提示**：与危险配置、暴露面相关                       |

| 模块路径                                         | 顶层功能                                                      |
| ------------------------------------------------ | ------------------------------------------------------------- |
| `src/entry.ts`、`src/index.ts`、`src/library.ts` | **进程入口、库导出**：将上述模块组合为可执行 CLI 与可引用 API |

## 5. 扩展与客户端：`extensions/`、`apps/`、`ui/`

### 5.1 `extensions/`（捆绑插件树）

- **出处**：`extensions/*`
- **架构角色**：默认工作区内的 **Channel / Provider / 其它插件包**，通过 manifest 与 `src/plugins/` 加载逻辑进入 Gateway 与 Agent 视野；是「核心保持扩展无关、扩展自我注册」的主要载体。
- **与 Phase 文档关系**：Phase3 自定义渠道、Phase2 插件 HTTP 路由、Phase4 Provider/工具扩展，均主要落在此树与 `src/plugin-sdk/`。

### 5.2 `apps/`（原生客户端）

- **出处**：`apps/android/`、`apps/ios/`、`apps/macos/`、`apps/shared/`
- **架构角色**：**operator / node** 双角色连接、设备身份、TLS 等与 Gateway 对齐的实现（Phase1）。
- **注意**：与 `src/gateway` 协议文档对照时，以 **Swift/Kotlin 共享通道实现** 与 **`src/gateway/protocol`** 为权威契约两端。

### 5.3 `ui/`（Web 控制面）

- **出处**：`ui/`
- **架构角色**：浏览器内 **长连接 Gateway 客户端**、Control UI 安全上下文与设备令牌策略等（Phase1、Phase2）。

## 6. 数据与控制流（概念级）

下列为**逻辑流向**，不绑定单一函数调用链：

1. **外部用户消息**（Telegram、Slack、插件渠道等）进入对应 **Channel 实现或扩展**，构造统一入站上下文，进入 **`src/auto-reply/`** 派发链路（Phase3）。
2. **控制面或 HTTP 兼容请求**（CLI、Web UI、OpenAI 兼容客户端）进入 **`src/gateway/`**，完成鉴权、scope、方法路由后，可能触发 **聊天发送、agent 调用、会话操作、节点调用** 等（Phase2）。
3. **需要模型与工具的一轮推理**由 **`src/agents/`** 嵌入式运行时（及必要时 **ACP 路径**）执行；工具可来自核心、插件、MCP；技能与记忆通过配置与工作区注入（Phase4）。
4. **回复**经 **`src/auto-reply/`** 与 **`src/infra/outbound/`**（及渠道适配器）回到原渠道或指定投递目标（Phase3）。
5. **扩展能力**通过 **`src/plugins/` + `src/plugin-sdk/` + `extensions/`** 增加方法、HTTP 路由、渠道、Provider、服务等，而无需把业务分支写死在 Gateway 核心（Phase2、Phase4）。

## 8. 小结

OpenClaw 的顶层架构可概括为：**Gateway 统一接入与控制面**，**自动回复 + 渠道契约统一消息面**，**Agent 运行时统一推理与工具执行**，**插件与工作区扩展承载差异化集成**；仓库通过 **`src/` 承载核心逻辑**、**`extensions/` 承载捆绑扩展**、**`apps/` 与 `ui/` 承载多端客户端**，形成完整闭环。

更细的协议字段、方法列表与 Channel I/O 字段要求，请以 **`docs/gateway/protocol.md`** 及 Phase1～4 专题文档为准；本文仅提供**系统级蓝图与代码出处索引**。
